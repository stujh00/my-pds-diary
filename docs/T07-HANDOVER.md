## 인증 전환 설계 — 아직 구현하지 않음

현재 DB는 `pds_workspaces.owner_id`를 비워 둡니다. T06에서 사용자 계정/회원가입/로그인을 만들지 않았습니다. 테이블의 workspace → plan → task 관계를 통해 T07 소유권 정책을 적용할 수 있습니다.

1. Supabase Auth로 가입/로그인/로그아웃을 추가하고 첫 화면을 로그인 화면으로 변경합니다.
2. **기존 공개 GET/POST `/api/diary`를 먼저 닫고**, 서버에서 세션/토큰을 검증합니다. 비로그인 요청은 401, 다른 사용자의 ID를 요청하면 403 또는 정보 유출을 피한 404로 거절합니다.
3. 기존 공개 자료를 누구나 가져가는 ‘첫 로그인 사용자가 소유’ 로직을 만들지 않습니다. 관리자가 검증한 본인 사용자 UUID에만 기존 workspace를 한 번 귀속합니다. 백업하고 트랜잭션으로 처리합니다.
4. 로그인 사용자마다 workspace를 분리합니다. 클라이언트가 보낸 owner_id를 신뢰하지 않습니다.
5. 가능하면 로그인 사용자의 JWT와 publishable key를 사용하는 DB 클라이언트로 전환하여 RLS를 적용합니다. service role/secret key는 RLS를 우회하므로 일반 사용자 요청에 그대로 쓰지 않습니다.
6. 모든 표에 SELECT/INSERT/UPDATE/DELETE RLS 정책을 작성합니다. 하위 표도 plan/task를 거쳐 workspace.owner_id=auth.uid()인지 검사합니다. 내보내기, 계획 이력, 완료 이력, 돌아보기, 오류 응답도 같은 범위를 적용합니다.
7. `pds_snapshot()`의 전체 자료 조회와 `pds_mutate()`의 고정 workspace/전역 요청키를 사용자 범위로 다시 작성합니다. requests는 workspace/user 범위의 중복 키로 바꾸고, RPC 권한과 직접 REST 접근 모두 검사합니다.
8. 기존 T06 공개 배포/Preview URL에서 같은 DB를 읽는 서버가 계속 남아 있으면 T07 DB가 노출될 수 있습니다. T07용 별도 DB로 복사해 전환하거나, 이전 공개 배포 경로를 끊고 해당 키를 폐기·교체합니다. T06 공개 코드 커밋 자체는 그대로 보존합니다.
9. 동일 사용자 성공 요청과 비로그인/다른 사용자 거절 요청을 짝지어 기록합니다. 브라우저 화면 숨김만으로 통과했다고 쓰지 않습니다.

## 실제 5일 관찰

질문 예시: ‘예상 시간을 어떻게 잡으면 실제 공부 시간과의 차이를 줄일 수 있는가?’ 최종 질문·지표는 T07 시작 시 본인이 결정합니다.

- 고정 지표 후보: 실제−예상 차이(분), 완료 수(개), 막힌 할 일 수(개).
- 질문·지표·단위·계산 규칙은 5일 동안 유지합니다.
- **3일차 전에** 계획 규칙만 한 번 바꿉니다. 예: Day 2 종료 후 ‘프로그래밍 예상 시간에 복습 시간을 추가’합니다. 집계식 변경과 혼동하지 않습니다.
- 5일간 실제 원기록과 계획 규칙 변경 시각·변경 전후·배운 점을 남깁니다. 하루에 몰아 쓰지 않습니다.
- 공개 URL은 로그인 화면까지만, 원기록은 비공개로 둡니다.
- 플랫폼 선택 과정 기록은 날짜/순서 보조 자료이며 필수 승인 조건으로 취급하지 않습니다.

T07 설명서 여섯 항목의 정확한 제목/요구사항은 아직 제공받지 않았습니다. 상세 과제 조건을 받은 뒤 누락 여부를 매핑해야 합니다. 이 인계문으로 T07 완료를 주장하지 않습니다.
