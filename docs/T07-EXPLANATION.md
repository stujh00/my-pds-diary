# 인증 구현 설명서 — 구현 사실과 제출 전 작성할 부분

이 문서는 현재 소스의 구현 설명 초안입니다. 배포된 Supabase/Vercel에서 검사하지 않은 결과와 실제 5일 원기록은 완료했다고 쓰지 않습니다.

## ① 무엇으로 붙였나

인증 서비스 **Supabase Auth**와 서버 SDK **@supabase/supabase-js 2.117.2**를 사용했다. 비밀번호는 서비스의 bcrypt와 무작위 salt로 해시해 보관한다. Supabase Auth 내부 빌드 버전은 배포 환경에서 `provider-version.mjs`로 확인 후 기록한다.

다이어리의 로그인 상태는 **서버 세션**으로 관리한다. 로그인에 성공하면 Node.js `crypto.randomBytes(32)`로 세션 식별자를 만들고 HttpOnly·Secure·SameSite=Strict 쿠키로 전달한다. DB에는 식별자의 SHA-256 해시만 저장한다. 이 SHA-256은 비밀번호 해시가 아니라 256비트 난수 세션의 보관용이다. 세션의 최대 수명은 로그인 후 **1시간**이며 자동 연장은 하지 않는다.

## ② 왜 그걸 골랐나

기존 다이어리의 DB가 Supabase여서 Auth 계정 UUID와 workspace 소유자를 연결하기 쉽고 비밀번호 처리를 관리형 서비스에 맡길 수 있어서 선택했다.

검토했지만 선택하지 않은 방법은 **직접 bcrypt를 붙여 가입·비밀번호 검증까지 구현하는 방식**이다. 비밀번호 검증·가입 관리까지 직접 유지해야 하는 부담이 커서 선택하지 않았다. 앱의 세션 발급/폐기 코드는 직접 작성했고 비밀번호 해시 알고리즘을 직접 구현하지 않았다.

Supabase JWT만 검증하는 방식도 검토했다. 로그아웃 후 기존 접근 토큰이 만료 전까지 유효할 수 있어서 이 과제의 즉시 폐기 조건을 만족하기 위해 서버 DB에서 별도의 앱 세션을 확인한다. 브라우저는 Supabase JWT를 받지 않는다.

## ③ 어디를 어떻게 고쳤나

- **가입:** `public/auth-ui.js` → POST `/api/auth` (`api/auth.js` signup) → Supabase `auth.signUp`. SDK는 서버 전용이다. 가입 성공 후 로그인 화면으로 전환한다. 같은 이메일 계정이 추가로 만들어지지 않는다.
- **로그인:** `public/auth-ui.js` → `api/auth.js` login → `auth.signInWithPassword` → `lib/auth.js` issueSession → `pds_auth_sessions`. 응답에는 Auth 토큰/비밀번호를 넣지 않고 앱 쿠키와 만료 시각만 전달한다. 없는 이메일과 잘못된 비밀번호는 같은 안내를 반환한다.
- **로그아웃:** `public/app.js` logout → `api/auth.js` logout → `lib/auth.js` revoke. DB에서 해당 사용자의 모든 앱 세션을 revoked 처리한 뒤 쿠키를 지운다. 쿠키만 삭제하는 처리가 아니다. 비밀번호 변경도 현재 비밀번호를 검증하고 기존 세션을 폐기한 뒤 Auth 비밀번호를 바꾼다.
- **자료 조회:** `public/app.js` bootstrap/load → GET `/api/diary` → `lib/auth.js` user → `pds_auth_owner` → `pds_snapshot`/`pds_read`. 쿠키 해시를 DB의 살아 있는 세션과 비교하고 그 세션의 user_id로 주인을 결정한다. 목록·한 건 조회·내보내기·이력 모두 같은 소유자 경로를 사용한다.
- **자료 변경:** `api/diary.js` → `pds_mutate`/`pds_observe`. 주인을 먼저 검사하고 다른 사람의 plan/task ID는 404로 거절한다. 요청 본문의 owner_id나 헤더의 계정 ID를 믿지 않는다. 중복 요청 키도 workspace별로 분리했다.
- **DB 위치:** `supabase/003_t07_auth.sql`. 브라우저 anon/authenticated 역할에 표와 RPC 권한을 주지 않고 RLS도 켜 둔다. 서버 키는 RLS를 우회하므로 RPC의 주인 검사가 실제 경계다. 세션 확인 시 행 잠금을 잡아, 로그아웃과 겹친 변경도 폐기된 세션으로 새 요청이 진행되지 않게 한다. 로그아웃 응답 전에 진행 중이던 요청은 끝날 수 있으나 응답 뒤 시작한 재요청은 거절된다.
- **기존 자료 이전:** `004_assign_owner.template.sql`. 관리자가 본인 계정 UUID를 확인해서 기존 workspace를 한 번만 귀속한다. 기존 ID/날짜/값/단위를 유지한다. 첫 가입자에게 자동 귀속시키지 않는다.
- **옛 공개 경로 폐쇄:** 인자 없는 `pds_snapshot()`과 세션 없는 `pds_mutate(text,jsonb,uuid)`를 제거한다. 이전 T06 서버 코드로 새 DB 자료를 읽거나 변경할 수 없다.
- **계정 삭제:** 현재 비밀번호 재확인 후 `auth.admin.deleteUser`. 외래키 CASCADE로 소유 workspace와 모든 관련 기록을 삭제한다. 화면에 삭제 안내가 있다. 실제 삭제 검사는 테스트 계정에서 한다.

## ④ 안 열리는 것을 확인한 기록

다음 **다섯 묶음**에 성공 요청과 거절 요청을 나란히 넣는다. 실제 배포 기록 `local-data/t07-auth-evidence.md`에서 가져오고, 쿠키/비밀번호/토큰/키는 `[가림]`으로 표시한다. 아래 기대값은 실행 결과가 아니다.

| 확인 묶음 | 성공 요청 | 거절 요청 | 기록해야 할 추가 근거 |
|---|---|---|---|
| 1. 로그인 전후 | 본인 GET `/api/diary` 200 | 비로그인 같은 GET 401 | 자료 화면 직접 주소는 로그인 화면 |
| 2. 계정 인증 | 올바른 계정 POST `/api/auth` login 200 | 없는 이메일/틀린 비밀번호 401, 중복 가입 실패 | 실패 문구 동일, bcrypt 두 값 다름 |
| 3. 세션 폐기 | 같은 쿠키 GET `/api/diary` 200 | 로그아웃 뒤 같은 쿠키·주소·방식 401 | 비밀번호 변경 뒤도 이전 쿠키 401, 만료 시각 |
| 4. 타인 자료 | 본인 한 건 읽기/수정/삭제 성공 | A→B 및 B→A 읽기/수정/삭제 각각 404 | 소스 위치, 거절 전후 상대 자료와 건수 동일 |
| 5. 계정 위조와 목록 | 본인 목록/생성 성공 | 다른 plan_id에 생성 404 | URL/헤더/본문의 다른 owner_id 무시, 본인 목록만 반환 |

**제출 전 채울 부분:** 실제 요청 시각·상태 코드·비밀값을 가린 응답·배포 소스 고정 URL. 만료 설정은 3600초이며 내 계정 화면과 로그인 응답 expires_at로 확인한다. 원문 증거가 없으면 ‘검사 완료’라고 쓰지 않는다.

현재 로컬 검증은 실제 마이그레이션을 PGlite(PostgreSQL)에 적용해 실행한 결과다. 두 계정의 양방향 접근 제한/목록 분리/변경 전후 동일/요청키 격리/직접 DB 권한 거절/세션 폐기·만료/관찰 규칙·삭제 관계를 검사한다. **Supabase Auth 실제 가입·로그인, Vercel 배포, 실제 5일 사용은 별도 확인 대상**이다.

## ⑤ AI와 나

아래 세 줄은 사용자 본인의 실제 선택에 맞춰 완성한다. 하지 않은 일을 직접 했다고 쓰지 않는다.

- **AI에게 맡긴 일:** 인증 코드, DB 마이그레이션, 접근 제한 검사 코드와 설명서 초안 작성.
- **내가 직접 판단한 일:** [실제로 선택한 인증 방식·규칙·공개할 자료·증빙 결과 등을 본인 말로 기록]
- **AI 제안을 따르지 않은 일:** [실제 사례를 기록. 없다면 제안을 검토한 뒤 적용했고 따르지 않은 제안은 없었다는 이유를 기록]

## ⑥ 아직 못 막은 것

- **앱 자체의 계정별/IP별 실패 횟수에 따른 잠금은 구현하지 않았다.** Supabase의 기본 Auth 제한에 의존하며 반복 로그인 시도를 추가로 통제하지 못해 비밀번호 추측과 계정/서버 자원 남용 위험이 남는다.
- **두 번째 인증 수단(MFA)과 비밀번호 분실 시 재설정 화면은 없다.** 비밀번호를 탈취당하면 추가 인증 방어가 없고 비밀번호를 잊으면 앱에서 직접 복구할 수 없다.
- **이메일 인증을 껐다면 이메일 소유 확인이 없다.** 다른 사람의 이메일로 가입해 계정을 선점할 수 있다. 켜서 배포했다면 이 항목을 실제 설정에 맞게 수정한다.
- **브라우저/기기 자체의 악성코드와 서버 운영자·서버 키 탈취는 막지 못한다.** HttpOnly로 JS 쿠키 읽기를 줄이지만 손상된 기기나 서버 권한 탈취까지 방어하지는 않는다.
- **삭제는 운영 DB에서 즉시 제거하지만 별도의 백업 보존 정책/삭제 기한은 구현하지 않았다.** 사용자가 이미 내보낸 파일과 플랫폼 백업에 자료가 남을 수 있다.

## 실제 5일 관찰 — 실제 사용 후 채우기

질문·지표·계산 규칙과 처음 계획 규칙은 1일차에 정한다. 지표는 하루 실제 공부 시간, 단위는 분, 계산은 선택한 실행 기록 실제 시간 합계다. 누락은 미완료로 유지하고 0을 채우지 않는다. 중복 기록 ID와 날짜는 거절한다. 240분 초과는 실제 값임을 메모로 확인한 뒤 유지한다. 합계는 정수 분, 평균은 소수 둘째 자리까지 반올림한다. 주 시작은 월요일이고 날짜 기준은 Asia/Seoul이다.

| 일차 | 실제 서울 날짜 | 공부 시간(분) | 근거 실행 기록 ID | 계획 규칙/메모 |
|---|---|---|---|---|
| 1 | 실제 사용 후 작성 | | | 처음 규칙 |
| 2 | 실제 사용 후 작성 | | | 처음 규칙 |
| 규칙 변경 | 실제 변경 시각 | — | 1일차·2일차 ID | 새 규칙·바꾼 이유 |
| 3 | 실제 사용 후 작성 | | | 변경 규칙 |
| 4 | 실제 사용 후 작성 | | | 변경 규칙 |
| 5 | 실제 사용 후 작성 | | | 변경 규칙 |

화면 합계 = 다섯 값의 합. 전체 평균 = 합/5. 변경 전 평균 = (1일차+2일차)/2. 변경 후 평균 = (3일차+4일차+5일차)/3. 같은 단위와 계산 규칙으로 비교한다. 결과가 나빠져도 실제 결과대로 남긴다.

## 짧은 확인 방법 4줄

1. **어디로 가나요:** [최종 결과물 URL]의 로그인 화면으로 간다.
2. **세 단계 안에 무엇을 하나요:** 가입(필요하면 이메일 인증) → 로그인 → 본인 계획을 만들고 조회한다.
3. **무엇이 보이면 통과인가요:** 로그인 후 본인 자료가 보이고 로그아웃 후 자료 직접 요청은 401이며 자료 화면은 로그인 화면으로 이동한다.
4. **안 될 때는 무엇이 보이나요:** 인증 실패 시 같은 로그인 오류 문구, 비로그인 401, 타인 자료 404, DB 설정 실패 시 503과 설정 확인 안내가 보인다.
