## 2. DB 변경

백업은 이미 받았습니다. 기존 Supabase SQL Editor의 새 쿼리에 `supabase/003_t07_auth.sql`을 붙여 실행합니다. 기존 DB에서는 001/002를 다시 실행하지 않습니다. 003은 기존 자료를 지우지 않고 인증용 표와 관찰 표를 추가하며, 예전 공개 RPC를 제거합니다. 그래서 옛 배포가 과제7 자료를 공개하는 경로도 닫힙니다.

그다음 변경 소스를 기존 저장소에 반영해 Vercel을 재배포합니다. 현재 서버용 환경변수는 같은 DB를 쓰는 한 유지합니다. `LOCAL_HTTP=1`은 로컬 전용이며 배포에 넣지 않습니다.

이메일 인증은 [T07-EMAIL-CONFIRMATION.md](T07-EMAIL-CONFIRMATION.md)를 따라 Site URL과 Redirect URLs, Confirm signup 메일 템플릿을 설정합니다. 기본 localhost 주소를 그대로 두면 인증 후 오류 화면으로 이동하므로 실제 배포 주소를 사용합니다.

## 3. 본인 계정에 기존 자료 연결

1. 앱에서 본인 이메일로 가입하고 로그인합니다. 가입 시 이메일 인증 안내가 나오면 메일을 먼저 인증합니다.
2. Supabase Authentication → Users에서 본인 UUID를 복사합니다. 비밀번호나 토큰을 공유하지 않습니다.
3. `004_assign_owner.template.sql`의 UUID 표시 부분을 바꿔 실행하고 앱을 새로고침합니다.

새 계정의 비어 있는 workspace만 정리하고, 기존 workspace의 owner_id를 본인 UUID로 연결합니다. 기존 계획/할 일/로그/이력 ID·날짜·값은 변경하지 않습니다. 잘못된 UUID를 넣으면 타인에게 자료를 줄 수 있으므로 **본인 계정인지 직접 확인한 UUID만** 사용합니다.

사용자 백업의 전체 자료는 계획 3개, 할 일 15개(삭제 이력 포함), 실행 기록 6건, 돌아보기 1건, 계획 이력 4건, 완료 이력 6건입니다. 실제 공부 계획만 보면 현재 할 일 7개, 실행 기록 3건, 실제 시간 합계 90분입니다. 이동 뒤 같은 값을 확인해 캡처합니다.

## 4. 카드1 화면

가입 화면 → 로그인한 자료 화면 → 로그아웃 후 로그인 화면을 캡처합니다. 새 시크릿 창에서 `/diary`와 `/index.html`을 열어도 로그인 화면으로 이동하는지 확인합니다. DB 오류가 있는 화면은 성공 증거가 아닙니다.

동일 이메일 재가입은 실패해야 합니다. 존재하는 이메일+틀린 비밀번호와 존재하지 않는 이메일의 로그인 오류는 모두 `이메일 또는 비밀번호를 확인하세요.`이어야 합니다.

## 5. 카드2 bcrypt 저장 결과

버전: 서버 SDK `@supabase/supabase-js 2.117.2`, 관리형 Supabase Auth. 서비스 내부 빌드가 필요하다면 로컬 서버 환경변수를 설정한 뒤 아래를 실행합니다. 서비스가 버전을 노출하지 않으면 ‘관리형 서비스 빌드 버전 확인 불가, 사용한 SDK 2.117.2’라고 사실대로 적습니다.

```sh
node --env-file-if-exists=.env.local scripts/provider-version.mjs
```

동일한 비밀번호로 테스트 A·B 계정을 새로 만들고, SQL Editor에서 아래를 실행합니다. UUID 두 개를 실제 테스트 계정 UUID로 바꿉니다.

```sql
select id, encrypted_password
from auth.users
where id in ('TEST_A_UUID'::uuid, 'TEST_B_UUID'::uuid);
```

`encrypted_password`는 이름과 달리 bcrypt 해시입니다. `$2...` 형태로 입력했던 비밀번호 원문이 보이지 않고 두 값이 서로 다른지 확인합니다. **비밀번호 해시는 비교 증거로 사용할 수 있지만 실제 입력 비밀번호·쿠키·토큰·비밀키는 제출하지 않습니다.** Auth 표의 다른 민감한 열은 캡처하지 않습니다.

로그인 요청에는 인증을 위해 비밀번호가 HTTPS 본문에 실리는 것이 정상입니다. 제출할 요청 캡처에서는 password를 `[가림]`으로 바꿉니다. 응답과 서버 로그에 비밀번호 원문이 반환/기록되지 않는지를 따로 확인합니다. ‘요청에서 비밀번호가 아예 전송되지 않는다’고 쓰지 않습니다.

## 6. 카드3·4 실제 요청과 응답

로컬 Node.js 22 이상에서 `npm ci` 후 실행합니다. 이메일 인증을 켠 프로젝트에서는 먼저 별도 브라우저 가입·메일 인증으로 테스트하거나 아래 자동 생성 도구 대신 수동 요청을 사용합니다. 자동 생성 도구는 이메일 인증을 끈 **과제용** 설정을 대상으로 합니다.

```sh
node scripts/auth-evidence.mjs https://my-pds-diary.vercel.app
```

새 테스트 이메일 A·B와 같은 테스트 비밀번호를 터미널에서 입력합니다. 비밀번호 입력은 화면에 표시되지 않습니다. 기존 계정으로 실행하면 중복 가입에서 중단합니다.

이 도구는 실제 배포 응답을 받아 다음을 검사하고 `local-data/t07-auth-evidence.md`와 `.json`에 비밀값을 가려 저장합니다.

- 본인 조회/수정 성공, 비로그인 직접 요청 401.
- A→B와 B→A 각각 읽기·수정·삭제 404. 상대 계획에 자료 생성도 404.
- 공격 전후 상대 자료 전체가 같고 목록에 상대 자료가 없음.
- URL·헤더·본문에 상대 owner_id를 적어도 본인 자료만 사용함.
- 같은 주소 GET `/api/diary`, 같은 쿠키로 로그아웃 전 200/후 401.
- 비밀번호 변경 전 동일 요청 200/후 이전 쿠키 401.
- 같은 이메일 중복 가입 실패, 로그인 실패 문구 동일.
- B 테스트 계정 삭제 후 이전 쿠키 401. 본인 공부 계정은 삭제하지 않음.

**두 계정으로 로그인한 직후, 비밀번호를 바꾸기 전에 프로그램이 멈춥니다.** 같은 비밀번호를 사용하는 이 시점에 카드2의 두 bcrypt 해시를 SQL로 비교하고 캡처한 뒤 Enter를 누릅니다. 이후 접근 제한·로그아웃·비밀번호 변경·B 삭제를 검사합니다. A는 기록 확인용으로 남고 B는 삭제됩니다. A의 비밀번호는 처음 입력한 테스트 비밀번호로 복원됩니다.

네트워크 오류로 도구가 중단되면 일부 계정/자료가 남을 수 있습니다. 가린 결과 파일을 먼저 읽고, 다른 새 테스트 이메일을 쓰거나 남은 테스트 계정을 직접 정리합니다. 이 파일은 자동으로 GitHub에 올리지 않습니다. 제출 전 이메일/개인 기록도 공개 범위를 검토합니다.

만료는 로그인 시 응답의 `expires_at`, 내 계정 화면의 ‘로그인 후 1시간’, 서버의 3600초 설정을 증거로 남깁니다. 만료 실제 검사까지 하려면 로그인 때의 쿠키를 본인 환경에서만 보관하고 1시간 뒤 같은 요청으로 401인지 확인하되 제출물의 쿠키는 반드시 가립니다.

직접 DB 경로도 점검합니다. anon/authenticated 역할로 다이어리 표 또는 RPC를 호출하면 권한 거절이어야 합니다. SDK의 사용자 JWT를 사용해도 앱 서버의 소유권 검사를 우회할 수 없어야 합니다.

## 7. 비밀값·스크립트 점검

```sh
npm run build
node --env-file-if-exists=.env.local scripts/check-secrets.mjs
```

이 도구는 현재 소스·배포용 dist·로컬 전체 Git 이력의 비밀키/JWT 패턴과 설정된 실제 서버 키 값이 남아 있는지 검사합니다. 원문은 출력하지 않습니다. 원격에만 있는 브랜치와 과거 Vercel 배포 파일은 별도로 확인해야 합니다.

브라우저 Sources/Network 응답/Console과 Vercel 함수 로그에도 비밀번호·Supabase 서버 키·세션 값이 기록되지 않는지 확인합니다. 인증 응답의 `Set-Cookie`는 정상 세션 전달이므로 외부 제출에서는 가립니다. 로그인 요청 본문의 비밀번호도 가립니다.

스크립트 입력 검사: 테스트 할 일 제목 `<script>alert('XSS')</script>`를 저장하여 팝업 없이 글자 그대로 표시되는지 확인합니다. CSP가 추가 방어로 적용되고, 사용자 문자열은 화면 삽입 전에 escape합니다.

## 8. 실제 5일

마감일은 그대로 둡니다. ‘5일 관찰’에서 질문·첫 규칙을 먼저 저장하고 그날부터 실제 공부를 합니다. 그날 시작하고 저장한 실행 기록만 선택할 수 있습니다.

추천 질문: **한 번 공부 시간을 30분으로 줄이면 하루 실제 공부 시간이 늘어나는가?**

고정 지표: 하루 실제 공부 시간. 단위: 분. 계산: 선택한 실제 실행 기록의 actual_minutes 합계.

처음 규칙: 한 번에 60분을 공부한다.

변경 규칙 예: 한 번에 30분을 공부한다. 이것은 추천안이며 본인이 실제 적용할 규칙을 선택합니다.

1일차 → 다른 실제 날짜의 2일차 → 규칙 한 번 변경(시각/이유/1·2일차 ID 자동 저장) → 변경 뒤 공부한 3일차 → 4일차 → 5일차 순서로 저장합니다. 3일차 공부를 시작하기 **전**에 규칙을 바꿔야 합니다. 매일 마지막 공부를 마친 뒤 하루 기록을 한 번 저장하세요. 저장 후 다른 로그를 추가해도 이미 고정한 하루 값에 자동으로 추가되지 않습니다.

기록 없는 날은 0으로 꾸미지 않습니다. 날짜는 꼭 연속일 필요는 없으나 실제 서울 날짜 5일이어야 합니다. 시작한 날에 1일차를 저장해야 하므로 공부할 준비가 된 날에 관찰을 시작합니다. 질문·지표·계산식은 도중에 바꾸지 않습니다.

마지막에는 화면의 합계와 평균을 손계산과 대조합니다. 변경 전은 1·2일차 평균, 변경 후는 3~5일차 평균으로 같은 지표와 단위를 비교합니다. 결과가 나빠져도 그대로 남깁니다. ‘내 자료 전체 내보내기’에는 관찰·일차·규칙 변경 기록도 포함됩니다.

## 9. 제출

결과물 URL은 시크릿 창에서 로그인 화면까지 열려야 하고, 소스 URL은 계정 없이 코드가 보여야 합니다. 심사자에게 실제 공부 계정 비밀번호를 제공하지 않습니다. 5일 사용 전에는 과제7 전체 완료로 제출하지 않습니다.
